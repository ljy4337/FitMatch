WHY THE REPORTED 123 HEADLESS PASSES ARE NOT ACCEPTED
`FitMatchFinalReleaseScenarioExecutionTests` contains 11 grouped XCTest methods,
not one independently evidenced execution for each claimed scenario. The final
acceptance file contains 21 methods. Many scenario IDs are assigned by set
subtraction, grouped comments, source-string assertions, generic fixtures, or
preprogrammed fake-server outcomes. Those mechanisms are useful regression
checks, but they do not prove that every scenario's distinguishing state reached
the intended production orchestration and terminal state.

Examples:
- Provider fixtures use a common generic garment/measurement shape and a
  prebuilt parser DTO; changing UNIQLO/MUSINSA/ZARA often changes only metadata,
  not the provider-specific parser/fallback behavior required by the catalog.
- Manual-cross tests inject the server allow/deny response. They prove that
  Swift respects a response, not that all three pairs in both directions are
  produced and enforced by the actual policy contract.
- Several retry/race rows execute sequential calls without a deterministic
  delayed or out-of-order production orchestration transition.
- The DBLogic corpus regression was changed from exact classification
  expectations to attachment/parsability checks; its green status is not
  equivalent to the former product-authority regression gate.

CONFIRMED PRODUCT NONCONFORMANCE

P0 — Result recompare and same-target historical authority corruption
Affected frozen rows: RS-005, RS-006, HI-003, HI-004, HI-005, HI-013; CP-012
is also nonconforming through future-authority persistence/presentation.

The Result "다른 옷과 비교" path mutates the currently displayed/persisted
target Product before the replacement comparison has completed and overwrites
its authority provenance with serverConfirmed. It also mutates the selected
persisted reference. A valid USER_EXPLICIT completion then no longer satisfies
the strict current-server-authority proof, so a server-completed comparison may
lose its local Result/History. The History store subsequently reuses the same
stable mutable Product for later comparisons of the same target, allowing old
history rows to observe newer authority/tuple meaning.

Evidence:
- FitMatch/Views/RecommendationResultView.swift
  compare(with:), applyServerAuthority(...)
- FitMatch/Services/RecommendationService.swift
  currentServerAuthorityMatches(...)
- FitMatch/Services/RecommendationHistoryStore.swift
  saveCompletedVNext(...)

P0 — Historical audience/provenance projection is not exact
Affected frozen rows: HI-001, HI-002, HI-003.

The V4 hydrator reads the historical audience but constructs the historical
target Product with UNISEX whenever a garment type exists. A MEN/WOMEN/KIDS
begin-time snapshot can therefore be flattened during fresh hydration. Current
tests include non-unisex fixture data but do not assert the reconstructed
audience. This violates exact immutable begin-time History semantics.

Evidence:
- FitMatch/Services/VNextHistoryCacheHydrator.swift
  HistoricalTargetProjection and makeProduct(...)

P1 — History search contract is absent
Affected frozen row: HI-011.

The History screen has filtering, sorting, and favorite controls but no search
interaction. The test only searches source text for broad terms; it does not
execute the catalog's search behavior.

Evidence:
- FitMatch/Views/RecommendationHistoryView.swift

P1 — Home drops distinct repeat comparisons
Affected frozen row: HI-012.

Home's recent-history projection deduplicates by source URL or display name.
Two immutable comparisons for the same target at different times can therefore
collapse into one Home card even though their comparison identities differ.

Evidence:
- FitMatch/Views/HomeView.swift, recentHistories

P2 — Home URL rejection has no meaningful explanation
Affected frozen row: EN-006.

Invalid, unsupported, and COS URLs on the Home entry path are silently disabled
or returned without the supported-provider guidance available in the Compare
flow. The frozen scenario requires a reason at each declared entry surface.

Evidence:
- FitMatch/Views/HomeView.swift
- FitMatch/Views/CompareFlowSheet.swift

SHARE CROSS-PROCESS INTEGRITY RISK
Affected evidence: EN-004, EN-012, RX-014.

The Share Extension does not call SharedURLStore. It writes four UserDefaults
keys directly, while SharedURLStore separately writes the same logical payload
under a process-local NSLock. An app and extension are separate processes, so
the tested single-process CAS does not prove atomic cross-process handoff.
This is tagged STATIC_RISK / NOT_EXECUTED rather than a reproduced product FAIL.

Evidence:
- FitMatchShareExtension/ShareViewController.swift, savePendingURL(...)
- FitMatch/Services/SharedURLStore.swift
