P0-1 HISTORY EXACT IDENTITY

Root cause

The vNext completed path called the legacy RecommendationHistoryStore.saveUnique
policy. That policy matches Product by URL/code/name, falls back from a missing
ProductSize UUID to a size label, and removes same-product histories. Those rules
are valid only for the legacy/manual cache and violate immutable server UUID
identity.

Pre-fix regression evidence

- P0 history suite: 0 PASS / 2 FAIL.
- A same-URL/code/name legacy Product replaced the incoming server Product UUID.
- A same-label legacy size replaced the exact server ProductSize UUID.
- The authorized ProductSize UUID intersection became empty.
- Two completed comparisons for one target and different references collapsed to
  one history.

Minimal fix

- Added RecommendationHistoryStore.saveCompletedVNext as an explicit vNext-only
  persistence contract.
- It accepts only schema-v2 server-completed histories with a calculation snapshot.
- Product reuse is exact Product UUID only.
- ProductSize reuse is exact ProductSize UUID only.
- URL, product code, product name, and size label are never vNext identity
  fallbacks.
- History replay is idempotent only by exact immutable comparison/history UUID.
- Other histories for the same Product are retained.
- The legacy/manual saveUnique behavior remains separate and unchanged.
- CompareFlowSheet, ShoppingProductFormView, and the release Result path route
  server-approved history through saveCompletedVNext.
- Server completion remains before history creation/cache persistence. A rejected
  completion returns before saveCompletedVNext or session-cache store.

Post-fix assertions

- Exact server Product UUID preserved: PASS.
- Exact server ProductSize UUID preserved: PASS.
- Same URL/code/name with different Product UUID: PASS.
- Same size label with different ProductSize UUID: PASS.
- Same target with reference A/B retains two histories: PASS.
- Exact history-ID replay creates no duplicate: PASS.
- Authorized alternate-size UUID set survives disk persistence/reload: PASS.
- Completion-before-cache/rejection ordering: PASS.

P0-2 DELETED REFERENCE LIFECYCLE

Root cause

Immutable history hydration represented a missing historical reference as a normal
active UserFit. Every active Closet/picker surface queried all UserFit rows, and
closet sync treated the hydrated row as a mutation candidate. A soft-deleted
reference could therefore reappear locally and be re-upserted.

Pre-fix regression evidence

- Closet/hydration combined run exposed four failures, including a history-only
  snapshot entering the upsert pipeline.
- The dedicated hydration run failed because USER_EXPLICIT remained an ordinary
  source identity instead of a history-only representation. Equivalent runs also
  covered USER_EDITED and RETAILER_SNAPSHOT.

Minimal schema-free fix

- Reused the existing canonicalSourceIdentity field with reserved value
  fitmatch_vnext_history_reference_snapshot.
- Added computed isHistoryOnlyReferenceSnapshot/isActiveClosetItem state and a
  helper that makes a history snapshot non-reference and noneligible.
- A missing reference synthesized from immutable history is marked history-only
  only after its historical authority evidence is decoded.
- No new persisted field, SwiftData entity, model version, or migration was added.
- All active Closet and reference-picker surfaces filter to isActiveClosetItem.
- Closet mutation/reference sync filters history-only snapshots.
- History hydration still receives cached snapshots, so immutable past results
  remain readable.
- Final authoritative closet hydration still sees the cache row; if the same UUID
  is genuinely active remotely, the server row can safely reactivate it. A
  soft-deleted remote row remains absent and the history-only snapshot stays
  inactive.

Post-fix assertions

- USER_EXPLICIT / USER_EDITED / RETAILER_SNAPSHOT hydration coverage: PASS.
- Active Closet resurrection: 0.
- Active reference-picker resurrection: 0.
- Hydration-triggered upsert/reference mutation across two repeat syncs: 0.
- Exact remote tombstone/deleted authority remains intact in the lifecycle stub:
  PASS.
- Immutable history remains readable through the history-only reference: PASS.
- SwiftData stored schema change: 0.

P0-3 EXACT MULTI-REFERENCE DELTA

Root cause

Reference synchronization reduced local reference state to a single first item.
It did not compare exact local and remote states per clientItemID, so local
A=false/B=true left remote A=true whenever B remained selected.

Minimal fix

- Reconciles local and remote reference state by exact clientItemID.
- Local true / remote false sends set(true) for that exact item.
- Local false / remote true sends unset(false) for that exact item.
- Equal states send no mutation.
- Sets execute first and refresh authoritative state before unsets, preserving the
  DB atomic same-garment-tuple replacement contract.
- Remote-only rows are hydration input, never implicit unset intent. This preserves
  first-login empty-cache safety.
- No Swift global one-reference rule was introduced.

Post-fix assertions

- Remote A=true/B=true, local A=false/B=true: A unset exactly once; B mutations 0;
  refreshed A=false/B=true: PASS.
- Inverse A set: exactly one mutation: PASS.
- Same-tuple replacement: one server set, DB atomic replacement retained: PASS.
- First login with remote A/B and empty local cache: unset 0, then A/B hydrated:
  PASS.
- Converged repeat sync: mutation 0: PASS.
