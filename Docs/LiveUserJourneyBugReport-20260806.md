## FM-LIVE-001 — 공유한 상품의 비교 화면이 열리지 않음 (수정 완료, 실기기 최종 확인 필요)

- 심각도: **Critical / 출시 차단**
- 재현율: 최종 검증 2/2 쇼핑몰, 100%
- 영향: 앱의 핵심 진입 경로인 `쇼핑몰 공유 → 내 옷과 비교`가 끝까지 동작하지 않습니다. 사용자는 성공 메시지를 본 뒤 홈으로 돌아오지만 비교가 시작되지 않고 공유 URL을 다시 확인할 방법도 없습니다.

### 재현 절차

1. 유니클로 또는 무신사 기준 상품을 링크로 내 옷장에 저장합니다.
2. Safari에서 같은 쇼핑몰의 비교 상품 페이지를 엽니다.
3. Safari 공유 버튼을 누르고 FitMatch 공유 확장을 선택합니다.
4. `FitMatch에 추가했어요!`가 표시되면 `보러가기`를 누릅니다.
5. 최초 실행 시 iOS의 `'FitMatch'에서 열겠습니까?`에서 `열기`를 누릅니다.
6. FitMatch 복귀 후 45초 동안 화면을 확인합니다.

### 기대 결과

- 공유한 URL로 비교 플로우가 한 번만 열립니다.
- 상품 분석 후 분류 확인, 기준 옷 확인 또는 비교 결과 화면으로 진행됩니다.

### 실제 결과

- FitMatch 홈 화면에 그대로 머뭅니다.
- 로딩, 오류, 재시도, 대기 중인 공유 상품 안내가 전혀 표시되지 않습니다.
- 최근 비교 결과도 생성되지 않습니다.

### 유력 원인

`ContentView`가 앱 활성화와 딥링크를 별도 경로로 동시에 처리합니다.

- `scenePhase == .active`에서 `openPendingSharedURLIfNeeded()`가 공유 URL을 소비합니다.
- 이어서 `onOpenURL`의 `openCompareFromDeepLink()`가 다시 같은 진입을 처리합니다.
- 두 번째 처리 시 저장소가 이미 비어 있으면 `pendingCompareURL`을 `nil`로 바꾸고 새 `compareViewID`를 생성합니다.
- `MainTabView`는 연속된 비교 요청 중 기존 시트를 닫고 다음 요청을 대기시키므로, 빠른 중복 요청이 시트 표시 경쟁 상태를 만들 가능성이 큽니다.

이는 실행 결과와 코드를 함께 본 원인 추정이며, 수정 시 앱 로그로 처리 순서를 확정해야 합니다.

### 수정 권고

1. 공유 URL 진입을 단일 코디네이터에서 정확히 한 번만 처리합니다.
2. 최근 처리한 공유 요청 ID 또는 URL을 기준으로 `scenePhase`와 `onOpenURL`의 중복 처리를 제거합니다.
3. 딥링크가 왔지만 저장소가 비어 있을 때 진행 중인 `pendingCompareURL`을 `nil`로 덮어쓰지 않습니다.
4. 비교 시트 표시가 예약된 뒤에만 공유 URL을 소비하거나, 실패 시 복구할 수 있도록 URL을 유지합니다.
5. 앱 실행 중·백그라운드·완전 종료 상태를 각각 회귀 테스트합니다.

## FM-LIVE-002 — `보러가기`가 FitMatch를 전면으로 열지 못함 (실기기 확인 필요)

- 심각도: **Major**
- 재현율: 최종 검증 2/2, 100%
- 문제: 공유 확장에서 `보러가기`를 눌러도 FitMatch가 30초 안에 전면 앱으로 전환되지 않았습니다. 테스트가 실제 사용자의 수동 앱 전환에 해당하는 동작으로 FitMatch를 직접 활성화한 뒤에야 홈을 확인할 수 있었습니다.
- 사용자 영향: 성공 메시지 다음의 주 행동 버튼이 목적을 달성하지 못합니다. 사용자는 Safari 또는 공유 확장에 남고, 직접 FitMatch를 찾아 열어야 합니다.
- 코드 위험: 공유 확장이 responder chain에서 `UIApplication`을 찾아 앱을 여는 방식에 의존합니다. 이 방식은 OS 버전과 확장 실행 환경에 따라 성공 여부가 불안정합니다.
- 권고: 지원되는 앱 전환 방식과 실패 감지를 사용하고, 전환이 불가능한 환경에서는 처음부터 `FitMatch 앱을 직접 열어주세요`라는 정확한 안내와 복구 가능한 대기 상태를 제공합니다.

## FM-LIVE-003 — 실제 비교 시작 전 성공으로 확정함 (문구 및 URL 보존 수정 완료)

- 심각도: **Major**
- 재현율: 2/2, 100%
- 문제: 공유 확장은 URL을 앱 그룹에 저장한 직후 `FitMatch에 추가했어요!`라고 표시합니다. 이후 OS가 딥링크 열기 요청만 수락해도 확장을 종료합니다. FitMatch가 URL을 소비하고 비교 화면을 열었는지는 확인하지 않습니다.
- 사용자 영향: 실제로는 비교가 시작되지 않았는데 성공했다고 안내하며, 확장이 닫힌 후 재시도나 URL 복구 수단이 없습니다.
- 권고: 문구를 `FitMatch로 전달했어요`처럼 실제 보장 범위에 맞추고, 앱 홈에 `공유한 상품 비교 이어하기` 복구 상태를 제공해야 합니다. URL은 비교 플로우 표시가 확인되기 전까지 삭제하지 않는 편이 안전합니다.

## FM-UX-004 — 공유 확장 표시 이름이 개발용 명칭임 (수정 완료)

- 심각도: **Minor**
- 확인 방식: 빌드 설정 정적 확인
- 현재 설정: `CFBundleDisplayName = FitMatchShareExtension`
- 문제: 시스템 공유 시트에 기술적인 타깃명이 노출될 수 있어 사용자가 공식 FitMatch 기능인지 즉시 이해하기 어렵습니다.
- 권고: 표시 이름을 `FitMatch` 또는 `FitMatch로 비교`로 변경합니다.

## 앱 버그가 아닌 항목

- 유니클로의 쿠키 정책 창은 최초 방문 시 사용자가 허용 또는 거부해야 하는 쇼핑몰 웹 UI입니다.
- `'FitMatch'에서 열겠습니까?` 확인은 커스텀 URL 스킴 최초 실행 시 표시되는 iOS 시스템 동작입니다.
- 위 두 항목을 처리한 뒤에도 FM-LIVE-001은 동일하게 재현됐습니다.
