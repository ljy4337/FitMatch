## 권장 실행 방식
1. CSV를 시작 목록으로 사용하고 현재 공식 API를 매 실행 재조회. 실제 앱 parser/observation 경로를 재사용하고 원문은 파일에 저장. 사이트별 낮은 동시성·제한된 재시도·이어하기를 적용. 403/429는 차단·속도제한으로 별도 집계하고 반복우회 금지.
2. 정상 사용자 세션으로 exact product/variant/size를 등록하고 서버 재조회. 등록한 Closet 항목을 명시적으로 선택해 candidate/authorization/begin→실제 비교 engine→complete→History 재조회까지 실행하는 통합 실행기가 필요. 정상 제품끼리 서로 다른 상품·쇼핑몰 조합을 포함. 구현 완료/실행 성공을 이번에 주장하지 않음.
3. 대표 화면은 최신 빌드 아이폰에서 수동 확인. URL 붙여넣기→색상·사이즈 선택→등록→옷장 재진입→다른 상품 비교→비교할 옷 선택→결과·다른 사이즈·기록 확인. 시뮬레이터 없이 서버/로직 경로를 검증해도 실제 화면 조작 성공과 구분.

## 비용과 정확도
- 전체 545행을 AI가 하나씩 읽고 클릭하지 않음. 스크립트로 추출/중복검사/HTTP/사전대조/결과집계. AI는 신규 raw/category/계약 또는 실패 유형별 대표 로그만 분석.
- 최초 실행은 category×raw 의미×단위×제품구조×provider의 서로 다른 조합을 덮는 작은 표본 선정. 고정 회귀 표본 + 매번 새 공식 상품을 섞어 과거 데이터에만 맞는 수정을 방지.
- 성공은 HTTP200이나 parser 성공이 아니라 저장 재조회/비교 complete/결과 수치 및 identity 일치로 정의. 예상 안내, 외부차단, 앱 결함, 미실행을 별도 집계. 점수 정답은 독립 계산한 대표 케이스로 검증; 동일 로직 출력 재사용 금지.
- 기존 FitMatchReleaseLiveProductAuditTests는 live parser 읽기 전용. FitMatchHeadlessUserJourneyTests는 scripted fixture 응답. 어느 쪽도 실제 인증 등록/비교 완료의 대체 증거가 아님.

## DB 보완의 우선순위
- 카테고리: 이 파일은 category master가 아님. ZARA MAN/WOMAN/KID는 audience, UNIQLO 목록은 category 없음, MUSINSA는 일부 표시분류. 현재 상세API 공식category key/path를 얻고 서버 active policy의 승인 매핑과 diff. 미매핑은 사용자 선택; 상품명 추론으로 전역 확정 금지.
- 실측: raw 보존→source→parser/category별 alias→정확한 canonical mapping→active metric 참여를 각각 확인. alias 누락이면 기존 canonical을 재사용하되 단면/둘레/시작점/구성품이 같을 때만 추가. canonical 신규는 별도 필요성 검토. policy 자동확장 금지.
- 우선 후보: MUSINSA 총장/밑단 문맥, 상의 허리; UNIQLO 끈 포함 길이·이너·front-rise 및 등중심/래글런 소매의 실제 policy 참여. 확정 신규대상 아님.
- 원래 실측 없음, 0/결측/단위불명, 신체 권장표만 있는 경우는 사전 추가로 해결 불가. 적절한 보완안내를 성공 기대값으로 테스트.
- 미정의 장식 실측 하나가 있어도 유효한 다른 공통 실측으로 가능한 비교를 불필요하게 막지 않는지 검사. 반대로 모르는 항목을 임의 치환해 허용하지 않음.
- 예상 위험: parser version alias 불일치, active category policy 버전 불일치, canonical은 있으나 metric/Swift 전달 빠짐, 복합세트 구성품 섞임, 색상/size identity 불일치, 이전 원문/완료snapshot 재사용. 현재 결함 확정이 아니라 테스트 후보.
