현재 구현 관찰: `MeasurementComparisonEngine.swift:285–309`는 항목별 `clamp(round(100−5×abs(delta)),0,100)` 후 정수 항목점수의 가중 평균을 다시 반올림한다. `VNextComparisonEngineAdapter.swift:156–164`는 최종 정수점수 내림차순 → 가중 절대차 평균 오름차순 → 정확한 size UUID 문자열 오름차순이다. 이는 **관찰 사실이며 제품 승인 근거가 아니다**.

**유지 지지:** 과거 문서와 현재 코드가 기본 5점/cm 방향에서 일치하고, 기존 snapshot 불변 정책은 수치 보존을 요구한다. 현재 oracle로 회귀를 잡는 것은 유용하다.

**독립 승인으로 간주하는 데 반대:** 동일 구현을 설명한 문서와 그 구현으로부터 선택한 공식을 손계산해도 순환 근거가 사라지지 않는다. 현재 정책 문서는 상세 산술을 승인하지 않으며 과거 문서끼리도 공식·가중치·gate가 다르다.

독립 기대값을 확정하는 데 필요한 최소 결정은 다음 세 가지다.

1. **공식 적용 범위:** 승인된 cm 절대차마다 1cm당 5점 감점, 항목별 0–100 제한 후 서버 가중 평균을 현재 comparison group 경로의 공식으로 채택하는지.
2. **반올림:** 항목점수와 최종 평균을 각각 정수화하는지 또는 마지막만 정수화하는지, 정확한 `.5`를 어떻게 처리하는지. 예를 들어 원래 항목점수가 99.5/98.5이고 같은 가중치일 때, 두 단계 사사오입은 최종 100이고 마지막만 사사오입하면 99다. 어느 쪽이 제품 정답인지 필요하다.
3. **순위:** 최종 정수점수 → 가중 절대차 평균 → 정확한 UUID 문자열 순서를 채택하는지. 특히 점수와 차이가 모두 같을 때 UUID 정렬을 제품 동작으로 승인할지 필요하다. 표시 label/입력 순서로 identity를 대신하지 않는 원칙만으로 UUID 우선순위가 자동 승인되지는 않는다.

위 결정 전에는 `policy-expectations.json:39–55`의 UNRESOLVED와 `oracle.json`의 characterization 표기를 유지하는 것이 맞다. 본 감사에서 정답표를 수정하거나 새 정책을 선택하지 않았다.

이 감사에 전달된 사용자 표현은 **“받아온 실측 항목 값만 보여주라”**다. 이 말은 API가 제공하지 않은 항목/값을 만들지 말라는 뜻을 지지한다. 다만 실제 API가 제공한 0.0 행을 `-`로 표시하는 명시적 MUSINSA 예외까지 철회한다는 문구는 아니다. `PendingTests.md`의 “유효 양수만”, binding의 “zero measurements must not be displayed”는 해당 원문보다 구체적인 해석이다.

**zero-hidden을 지지하는 가장 강한 경우:** 10월 1일 복구 결정 이후 사용자가 MUSINSA 예외까지 포함해 0행을 숨기라고 명확히 다시 지시했다면, 그 최신 직접 지시가 문서보다 우선한다. 이 경우 현 구현과의 실제 제품 정책 충돌이 맞다.

**현재 BUG 확정에 반대하는 근거:** 현재 확인 가능한 명시 문서·Git·구현은 모두 `-` 정책에 일치한다. 후속 사용자 명시 철회가 없이 일반 문장을 “모든 0행 숨김”으로 확장하면 테스트가 새 UX 정책을 만들어낸다. 또한 과거 숨김 기록만 읽으면 그 이후의 대체 결정을 놓친다.

따라서 이전 raw_zero의 실제 assertion FAIL은 삭제하거나 PASS로 바꾸지 않는다. **현재 확인된 것은 `테스트 기대값과 현행 승인 문서의 충돌`이며, 제품 결함 여부에는 추가 권위 근거가 필요하다.** 정확한 후속 원문을 확보하면 기대값 변경 여부와 변경 이유를 새 기록으로 남길 수 있다. 기존 원문 corpus·해시·실패 증거를 조용히 바꾸거나, 통과를 위해 제품/정책을 수정해서는 안 된다.
