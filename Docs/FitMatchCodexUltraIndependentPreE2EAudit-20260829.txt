P0-1 — COMPLETED VNEXT HISTORY EXACT IDENTITY/PROVENANCE IS REWRITTEN

Symptom
After successful server completion, the local history store can replace the exact
vNext Product/ProductSize UUIDs with an older pre-vNext cached Product/size having
the same URL/code/name/size label. It also deletes other local histories for the
same Product.

Execution path
RecommendationService.makeCompletedVNextHistory
→ exact authorized product_size_id selected
→ CompareFlowSheet or RecommendationResultView completes server comparison
→ RecommendationHistoryStore.saveUnique
→ legacy URL/code/name product match
→ exact-ID miss falls back to normalized size label
→ incoming exact graph replaced/deleted
→ all same-product histories deleted.

Evidence
- FitMatch/Services/RecommendationHistoryStore.swift:13-26
- FitMatch/Services/RecommendationHistoryStore.swift:34-57
- FitMatch/Services/RecommendationService.swift:63-97
- FitMatch/Views/CompareFlowSheet.swift:1612-1643
- FitMatch/Views/RecommendationResultView.swift:2990-3031

Root cause
A legacy one-history-per-product and size-label dedupe policy is still used for a
server-authorized immutable vNext comparison whose identity contract is UUID-based.

Actual impact
- exact product_id/product_size_id provenance can be lost;
- the same label can bind to another variant/measurement graph;
- Other Size’s authorized-ID intersection can become empty;
- distinct server comparisons for the same target but different references are
  removed from immediate/offline local history;
- current Result/offline cache cannot be trusted as an exact server projection.

Minimal fix
Split server-completed vNext history persistence from legacy/manual dedupe. In the
vNext branch, reuse Product/ProductSize only by exact UUID, never by label, and
dedupe only by the exact immutable comparison/client-history ID. Preserve legacy
manual behavior separately. No DB architecture or SwiftData schema redesign is
required for this P0.

Regression risk
Changing the shared legacy store indiscriminately could duplicate old manual
histories. The vNext-only branch must be explicit.

Required tests
1. Pre-vNext same URL/code + same label + different UUID must retain server UUIDs.
2. Same target + two references must retain two completed histories.
3. Other Size authorized UUID intersection must remain exact after persistence.
4. Server completion rejection must create no local cache.

P0-2 — DELETED REFERENCE REAPPEARS AS AN ACTIVE CLOSET ITEM

Symptom
Deleting a reference removes the local UserFit and requests a server soft-delete,
but a later immutable history sync recreates the missing reference as a normal
UserFit. My Closet displays it as active.

Execution path
Closet delete
→ local history/UserFit delete + server soft-delete
→ immutable server comparison remains
→ comparison_history returns the soft-deleted reference_client_item_id
→ VNextHistoryCacheHydrator.makeReference creates a normal UserFit
→ MyClosetView’s unfiltered @Query displays it
→ userFits task identity schedules another closet sync.

Evidence
- FitMatch/Views/MyClosetView.swift:478-515
- FitMatch/Views/ClosetItemDetailView.swift:524-540
- supabase/migrations/20260829050000_vnext_swift_user_contract.sql:827-859
- FitMatch/Services/VNextHistoryCacheHydrator.swift:41-75
- FitMatch/Services/VNextHistoryCacheHydrator.swift:206-266
- FitMatch/Views/MyClosetView.swift:7-10,125-139,262-285
- FitMatch/ContentView.swift:56-70,173-190

Root cause
The cache model has no history-only/deleted/tombstone distinction. Hydration
represents an immutable historical reference by inserting the same active UserFit
entity consumed by My Closet and closet sync.

Actual impact
The explicit delete lifecycle cannot persist: the deleted garment and history are
visibly recreated, normally near the top because makeReference uses Date(). The
server closet row was not proven to reactivate; this P0 is the deterministic local
active-Closet resurrection and resulting delete UX failure.

Minimal fix
Represent history-only reference snapshots separately, or add an explicit
cache-only/tombstone contract excluded from active Closet queries, reference
pickers, and closet sync. If product UX says deletion hides historical entries,
skip rehydrating hidden/deleted client IDs. Preserve immutable server evidence.

Regression risk
Dropping the snapshot entirely could make historical Result unreadable. The fix
must separate historical presentation from active closet authority.

Required tests
1. Complete comparison with reference A.
2. Soft-delete A and delete local cache.
3. Run closet sync → history sync → task-triggered closet sync twice.
4. A active UserFit count = 0, active picker count = 0, remote deleted_at retained,
   A mutation RPC count = 0, immutable history still follows the selected UX rule.
5. Cover USER_EXPLICIT, USER_EDITED, and RETAILER_SNAPSHOT references.

P0-3 — MULTI-TYPE REFERENCE UNSET IS NEVER SENT

Symptom
When two references of different garment tuples are active, unsetting only one is
reversed after sync.

Execution path
server A=true / B=true
→ local user changes A=false / B=true
→ synchronizeReferenceAuthority sorts all local true references
→ sends set(true) only for requested.first (B)
→ never sends unset(false) for A
→ authoritative list still returns A=true
→ local A is reapplied true.

Evidence
- FitMatch/Services/FitMatchClosetSyncCoordinator.swift:276-297
- FitMatch/Services/FitMatchClosetSyncCoordinator.swift:233-258,663-695
- FitMatch/Views/MyClosetView.swift:380-470
- FitMatch/Services/ReferenceGarmentPolicy.swift:3-11
- supabase/migrations/20260829012836_vnext_closet_reference_api.sql:221-250

Root cause
The UI and DB support one reference per compatible garment tuple, but Swift sync
reduces all reference state to one globally selected item. It only sends unset when
there are no local references at all.

Actual impact
Reference unset is non-functional for an item whenever another type remains a
reference. The server remains stale and can continue selecting the unwanted basis
garment for automatic comparison.

Minimal fix
Diff local vs authoritative remote reference state by exact clientItemID and send
set/unset for every changed item. Preserve the DB’s same-tuple atomic replacement
behavior; do not choose a single global reference.

Regression risk
An unguarded initial empty cache must not clear remote references. Retain the
existing first-login/cache-owner protection while adding exact deltas.

Required tests
1. Remote A=true/B=true different tuples, local A=false/B=true.
2. Assert exact A unset once and no unnecessary B mutation.
3. Refresh must return A=false/B=true.
4. Cover inverse set, same-tuple replacement, and first-login empty-cache safety.
