# FitMatch 실측 표시·저장·비교 정책

## 1. 목적과 적용 범위

이 문서는 쇼핑몰 상품 링크로 받은 의류 실측 원본 데이터를 내 옷 등록 화면에 표시하고 저장하는 방법과, 상품 비교에서 실측 항목을 선택하는 기준을 정의한다.

대상은 MUSINSA, UNIQLO, ZARA 등 쇼핑몰 API 또는 공식 상품 데이터에서 받은 **상품 사이즈별 의류 실측값**이다. 신체 권장 치수, 모델 신체 정보, 일반 사이즈 가이드처럼 실제 상품 치수가 아닌 값은 의류 실측 원본과 분리하며 이 정책의 직접 비교 대상이 아니다.

## 2. 용어

- **쇼핑몰 원본 실측**: 쇼핑몰이 제공한 항목 코드·표시명·값·단위·측정 기준·구성품 정보를 원형대로 보존한 데이터.
- **동일 실측 구조**: 동일 쇼핑몰 안에서 같은 원본 실측표 schema/parser 구조를 사용하고, 항목 identity·측정부위·측정 시작점과 끝점·단면/둘레·구성품·단위 의미가 동일한 구조. 상품명이나 화면 표시명만 같아서는 동일 구조가 아니다.
- **동일 원본 실측 항목**: 동일 실측 구조 안에서 안정적인 원본 항목 코드와 의미가 일치하는 항목. 예: UNIQLO `body-width` ↔ `body-width`, ZARA `zone-name-chest` ↔ `zone-name-chest`.
- **FitMatch 기준 실측항목**: 검증된 원본 실측을 FitMatch canonical code, 단위, basis와 의미로 변환한 항목.
- **비교 가능 실측**: 서버가 현재 비교 정책, 의미, 단위, 구조, identity 및 권한 검증을 통과시켜 해당 비교에 사용하도록 승인한 항목.

## 3. 내 옷 등록 정책

1. 선택한 상품·variant·size 중 **사용자가 선택한 사이즈**에 대해 쇼핑몰 API에서 받은 의류 실측 원본 데이터를 등록 화면에 **실제 유효 숫자값(유한한 양수)이 있는 항목을 모두 표시한다**. 무신사 API의 0값 항목은 행을 보존하고 값 대신 `-`로 표시한다. 그 외 0·음수·비정상 숫자는 실측 행으로 표시하지 않는다. 원본 보존 범위는 표시 필터와 별개다.
2. canonical 매핑 여부를 이유로 원본 항목을 숨기지 않는다. 매핑되지 않았거나 비교에 사용할 수 없는 항목도 원본 항목임을 구분해 표시한다.
3. 저장 시 화면에 표시한 원본 실측을 DB에 모두 저장한다. 원본과 FitMatch canonical 결과는 별도 데이터로 보존한다.
4. 각 원본 실측에는 가능한 범위에서 다음 정보를 함께 보존한다.
   - 쇼핑몰과 parser/version
   - 원본 항목 코드와 표시명
   - 원본 값과 단위
   - 측정 기준과 측정부위
   - 본체·안감·페티코트 등 구성품
   - 정확한 product·variant·size identity
   - canonical 변환 상태와 사용한 사전/version
5. 미매핑, 모호함, 지원하지 않는 단위, 0 또는 비정상 값은 원본에서 삭제하거나 다른 값으로 꾸미지 않는다. 원본의 상태와 사유를 보존하고 비교 입력에서는 제외하거나 차단한다. 2026-10-01 표시 정책에서 무신사 API의 0값은 원본 0을 유지하면서 화면에 `-`로 표기한다. 다른 쇼핑몰의 0·음수·비정상 숫자 행은 숨긴다. 정상 양수인 unknown/미매핑 항목은 계속 표시한다.
6. 내 옷 저장 성공은 서버의 원본 및 canonical snapshot 저장과 authoritative read-back이 완료된 뒤에만 표시한다.

## 4. 상품 비교 정책

### 4.0 FitMatch 비교 그룹 경계

- 비교 대상 상품과 내 옷은 서버가 확인한 동일한 FitMatch comparison group 코드(A–G) 안에서만 비교한다.
- 쇼핑몰 카테고리 이름이나 세부 의류 종류의 일치는 요구하지 않는다. 따라서 같은 그룹의 반팔과 긴팔은 아래 실측·semantic 검증을 통과할 때 비교할 수 있다.
- 서로 다른 그룹은 공통 실측이 있어도 후보·eligible sizes·authorization·begin에서 허용하지 않는다.
- 서버가 그룹을 찾지 못한 UNMAPPED 상품만 사용자가 A–G를 선택할 수 있다. 이 선택은 현재 비교 세션의 서버 검증 문맥일 뿐, 쇼핑몰 전역 매핑·상품 영구 분류·옷장 그룹을 바꾸지 않는다.

| 비교 조건 | 사용할 실측 |
|---|---|
| 동일 쇼핑몰 + 동일 실측 구조 | 동일 원본 실측 항목끼리 직접 비교 |
| 동일 쇼핑몰 + 다른 실측 구조 | 양쪽 모두 연결되는 FitMatch 기준 실측항목만 비교 |
| 다른 쇼핑몰 | 원본 이름이나 구조의 유사성과 관계없이 양쪽 모두 연결되는 FitMatch 기준 실측항목만 비교 |

### 4.1 원본 실측 직접 비교

- 동일 쇼핑몰이면서 동일 실측 구조인 경우에만 동일 원본 실측 항목끼리 직접 비교한다.
- source, parser/schema 구조와 안정적인 원본 항목 identity를 확인한다.
- 동일 쇼핑몰이어도 실측표 구조가 다르면 원본 항목을 직접 비교하지 않는다.
- 다른 쇼핑몰끼리는 원본 항목명이 우연히 같거나 의미가 유사해 보여도 원본 항목을 직접 비교하지 않는다.
- 단위가 환산 가능한 경우에도 검증된 변환만 허용한다. 의미가 다른 값을 수치만 변환해 비교하지 않는다.

### 4.2 FitMatch 기준 비교

- 동일 쇼핑몰·동일 실측 구조가 아닌 모든 경우에 적용한다.
- 원본 항목끼리 직접 비교하지 않는다.
- 양쪽 원본이 각각 검증된 FitMatch canonical 항목으로 변환되고, 동일한 canonical code·unit·basis를 공유할 때만 비교한다.
- 공통 mapping이 없는 원본 항목은 저장·표시하되 비교에서 제외한다.
- 공통 FitMatch 기준 실측항목이 없으면 비교를 진행하지 않는다.

### 4.3 서버 승인과 점수

- 비교 그룹은 비교 가능한 정책 문맥을 선택하지만 원본 실측의 의미를 바꾸지 않는다.
- 후보 조회, eligible sizes, authorization, begin은 같은 canonical/policy context와 정확한 product·variant·size·Closet identity를 사용한다.
- 최종 점수에는 서버 begin snapshot이 승인한 실측만 사용한다. 원본이 저장·표시되었다는 사실만으로 점수 항목에 자동 포함하지 않는다.
- 단면과 둘레, 앞길이와 뒷길이, 일반 소매와 등 중심/래글런 소매, 본체와 부속 구성품처럼 기준이 다른 항목을 임의로 동일 취급하지 않는다.
- 의미·단위·basis가 모호하거나 충돌하면 추정값이나 첫 번째 항목으로 대체하지 않고 fail closed 또는 명시적 보완 상태로 처리한다.
- `RETAILER_EXACT`는 같은 쇼핑몰의 같은 검증 schema와 원본 semantic identity가 서버에서 모두 증명된 경우에만 가능한 evidence mode다. source/parser/schema, raw identity, unit, basis, representation, component가 모두 일치해야 하며 raw label/raw code만 같다는 사실은 충분하지 않다.
- 20260924의 v2 helper 후보는 점수 미포함 proof만 만들며, candidate·authorization·begin·complete·History의 활성 비교 경로를 바꾸지 않는다. 실제 점수 mode 승인은 별도 서버 snapshot 계약과 end-to-end 검증 전까지 활성화하지 않는다.
- 서버가 승인한 같은 그룹 후보는 목록으로만 표시한다. Swift는 첫 후보를 선택하거나 비교·History 생성을 시작하지 않으며, 사용자가 특정 Closet 항목을 누른 뒤에만 authorization·begin·complete를 실행한다.
- 비교 화면에서 사용자가 고르는 분류는 A–G 상위 그룹뿐이다. 상세 의류 종류 선택·확인 UI는 비교 권한을 만들거나 복구하는 수단이 아니다. 서버가 상위 그룹만으로 안전한 문맥을 만들지 못하면 Swift가 세부 분류나 상품명으로 보완하지 않고 명시적으로 종료한다.
- 공통 canonical 실측이 1개 이상인 경우에만 서버가 비교를 허용한다. 같은 그룹이거나 화면에 원본 실측이 있다는 사실만으로 비교를 허용하지 않는다.
- 핏 매칭 점수와 신뢰도는 별도 표시한다. 신뢰도는 서버 snapshot에서 실제 점수에 사용한 승인 실측 항목 수로 계산하며 coverage 비율은 별도 정보일 뿐 신뢰도에 섞지 않는다.
- 상의 정책의 승인 실측 가중치는 가슴 2.0, 어깨 1.5, 총장 1.0, 소매 1.0이다. 앱의 embedded fallback은 표시용 보조값일 뿐, 서버 snapshot과 다를 때 서버 값을 대체하지 않는다.

### 4.4 1차 출시 점수 산술과 추천 순서

2026-10-02 사용자가 계산 알고리즘 결정을 에이전트에게 위임한 뒤, 1차 출시에는 기존 검증 동작을 유지하는 다음 규칙을 제품 기준으로 확정했다. 이는 실측 유사도 규칙이며 실제 착용감·신체 적합성의 통계적 확률이나 최적 정확도를 입증한 모델이 아니다. 서버 승인·의미·단위 검증, 원본 저장, 과거 snapshot은 그대로 유지한다.

- 입력은 서버 begin snapshot이 승인한 동일 의미·단위의 실측과 양수 가중치다. cm로 검증된 차이를 사용하며 누락값·잘못된 evidence를 0이나 기본값으로 대신하지 않는다.
- 항목 i의 절대차를 `d_i`, 서버 가중치를 `w_i`라 하면 항목점수는 `s_i = max(0, min(100, round(100 - 5 × d_i)))`이다.
- 최종 정수점수는 `round(Σ(w_i × s_i) / Σw_i)`이다. 실제 비교된 승인 항목만 사용한다. 공통항목·최소개수·필수항목 조건은 서버 계약을 따라야 한다.
- `round`는 가장 가까운 정수로 반올림하고 정확한 절반은 0에서 멀어지는 방향으로 처리한다. 항목점수와 최종 가중평균을 각각 반올림한다. 예: 97.5·92.5에 가중치2·1.5면 98·93 → 최종96점이다.
- 추천 순서는 최종점수 내림차순 → 가중 절대차 평균 `Σ(w_i × d_i) / Σw_i` 오름차순 → 정확한 `productSizeID.uuidString` 사전식 오름차순이다. 마지막 순서는 완전 동점의 일관성만 보장하며 착용감·더 작은 사이즈 우선이라는 뜻이 아니다. label·배열 첫 항목으로 identity를 대체하지 않는다.
- 신뢰도(사용한 승인 실측 수)와 coverage는 점수와 별도로 유지한다. 높은 점수를 높은 신뢰도 또는 착용 성공 확률로 해석하지 않는다.
- 이미 완료된 History는 당시 snapshot을 재현한다. 이 문서화 때문에 과거 점수나 순위를 재계산하지 않는다.

## 5. 표시·저장과 비교의 분리

- **표시·저장 범위**는 쇼핑몰이 제공한 의류 실측 원본 전체다.
- **비교 범위**는 위 매트릭스와 서버 정책을 통과한 공통 실측만이다.
- 따라서 화면과 DB에 존재하는 원본 실측 개수는 실제 점수에 사용되는 실측 개수보다 많을 수 있다. 이는 정상 동작이며 누락으로 간주하지 않는다.
- 과거 비교 결과는 당시 승인된 snapshot으로 유지한다. 사전이나 정책이 변경돼도 조용히 재계산하지 않는다.

## 6. 구현·검증 원칙

- retailer parser는 원본 사실을 제공하며 canonical 정책을 추론하지 않는다.
- Swift는 원본 전체를 표시하고 정확한 identity를 전달한다. 서버 권한이나 비교 항목을 로컬에서 새로 만들지 않는다.
- DB/server는 원본 보존, canonical 변환, 비교 정책 선택, authorization과 snapshot의 권위다.
- 회귀 검증은 최소한 원본 수신 개수, 화면 표시 개수, DB 원본 저장 개수, canonical 변환 개수, 정책 선택 개수, 공통 승인 항목 개수를 각각 확인한다.
- 동일 쇼핑몰·동일 구조, 동일 쇼핑몰·다른 구조, 다른 쇼핑몰 조합을 각각 검증한다.
